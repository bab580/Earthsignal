# MASTER BUILD PROMPT — EARTHSIGNAL

You are the senior product engineer and technical lead working with Texora Tech Solutions. Build EarthSignal as a working, scientifically honest MVP for a NASA Space Apps Challenge demonstration.

## Product purpose

EarthSignal helps people understand how environmental conditions vary by location and time by making NASA Earth-observation and analysis-ready environmental datasets easier to inspect. The Uganda-focused MVP uses NASA POWER for precipitation and air temperature, with optional NASA AppEEARS/MODIS point samples for vegetation and daytime land-surface temperature.

The Space Crop Research workspace also supports controlled Earth-based growing studies: experiment groups, habitat measurements, plant-growth observations, harvest records and descriptive resource-efficiency calculations. Spaceflight research is scientific context only; EarthSignal does not reproduce or claim microgravity conditions.

## Non-negotiable requirements

1. The app must retrieve live data from the official NASA POWER API. Do not use fabricated values, hardcoded chart arrays, placeholder API responses or generated data in the live-data path.
2. Show the source, product/service name, parameter codes, units, coordinates, selected period and retrieval time.
3. Show errors clearly when the upstream API fails, times out, returns invalid JSON or lacks data.
4. Never silently fall back to mock data.
5. Clearly distinguish NASA data from ground sensor readings.
6. Do not claim POWER data is a direct measurement at the farm or that it is all direct satellite data. Describe it accurately as NASA POWER analysis-ready meteorological/solar data and identify the selected variables.
7. Do not claim that the MVP predicts drought, flood, crop failure or yield.
8. Design for a live demonstration on a laptop with a clear, uncluttered interface.
9. Validate coordinates, date ranges and API inputs on the backend.
10. Keep NASA API calls server-side where possible, apply timeouts and return actionable errors.
11. Keep NASA Earthdata credentials on the server and never include them in browser responses.
12. Explain historical evidence with deterministic statistical summaries; do not imply that explanations are generated by AI.
13. Keep experiment, habitat, farmer sensor and remote-observation records distinguishable by source, timestamp, units and location/experiment context.
14. Do not invent plant observations, harvests, calibration values, nutrition facts or sensor readings. Missing measurements remain missing.
15. Require source references for crop nutrition values and do not infer nutrition from environmental sensors.
16. Label water-use calculations as exploratory; they are not automatically equivalent to validated crop-water-productivity measures.

## MVP user journey

- User opens EarthSignal.
- User selects a preset Ugandan location: Kampala, Lira, Gulu, Mbale or Mbarara.
- User can adjust latitude/longitude.
- User selects a start and end date.
- User selects precipitation and/or temperature.
- User clicks Load NASA data.
- Backend calls NASA POWER daily point API using JSON.
- Frontend renders the real returned series, a summary and provenance.
- Dashboard can optionally load MODIS NDVI and daytime land-surface temperature when free NASA Earthdata credentials are configured.
- Historical analysis surfaces seasonal anomalies and exploratory trends, with limitations clearly shown.
- User can change location and repeat the analysis.
- User can create a controlled-growing study with control and treatment groups.
- User can save timestamped environmental readings, plant observations, harvest weights and habitat/resource measurements.
- EarthSignal calculates growth and fresh/dry water-use summaries only when their required measured inputs exist.
- User can save crop profiles with references for any nutrition information.

## Initial technical architecture

- Backend: Python 3.10+, FastAPI, httpx, Pydantic.
- Frontend: static HTML, CSS and JavaScript served by FastAPI for the first hackathon build.
- Charts: Chart.js from a pinned CDN version or a locally bundled copy.
- Map: Leaflet with OpenStreetMap tiles; map is a location selector, not a NASA data layer.
- Data: NASA POWER daily point API and optional NASA AppEEARS MODIS point sampling.
- Research data: SQLite records experiments, treatment groups, sensor/device metadata, environmental readings, plant observations, harvest records and sourced crop profiles separately from NASA and farmer records.
- Sensor website path: ESP32 → authenticated JSON POST → FastAPI → SQLite. Firmware connectivity and offline retry support require separate hardware validation.

Do not add user accounts, payments, complex roles, a vector database, a chatbot framework, Kubernetes or microservices to this MVP. The device token protects only sensor ingestion; it is not user authentication.

## NASA POWER integration

Use the documented daily point endpoint:

https://power.larc.nasa.gov/api/temporal/daily/point

Query parameters:
- parameters=PRECTOTCORR,T2M
- community=AG
- longitude=<longitude>
- latitude=<latitude>
- start=YYYYMMDD
- end=YYYYMMDD
- format=JSON
- time-standard=UTC

The exact available parameter codes and units must be read from the response metadata or verified against current NASA POWER documentation. Do not guess units.

The backend should:
- Make a request with a 30-second timeout.
- Check HTTP status.
- Parse the NASA response structure.
- Extract `properties.parameter` time series.
- Extract `parameters` metadata and units if supplied.
- Preserve missing-value markers as missing values, not zero.
- Return a normalized response with `source`, `parameters`, `location`, `period`, `retrieved_at`, `observations`, and `metadata`.
- Return 502 with a useful message if NASA is unavailable.

## Scientific behaviour

The MVP may calculate:
- Count of valid daily observations.
- Mean, minimum and maximum for the selected period.
- Monthly aggregation from daily observations, clearly labelled as calculated by EarthSignal.
- Missing-data count.

Historical anomaly screening compares a complete calendar month with earlier complete observations from that same calendar month and requires at least three baseline years. Trend analysis uses complete calendar-year means, reports Mann–Kendall and Sen's slope, and requires documented coverage and sample thresholds. Label the results exploratory: significance tests do not establish causation and do not account for all climate-series assumptions. Neither analysis is a forecast.

Generate plain-language explanations deterministically from the measured values and statistical outputs. Do not send user data to or imply use of a generative AI service.

## SoilSense sensor integration

Use the separate prototype endpoint:
POST /api/sensors/readings

Request fields:
- `device_id`
- `raw` (12-bit ADC value, 0–4095)
- `moisture` (firmware-calculated percentage, 0–100)
- `status` (`DRY`, `MOIST` or `WET`)
- `recorded_at` (optional ISO-8601 timestamp)

Require `X-Device-Token` when `EARTHSIGNAL_DEVICE_TOKEN` is configured; unauthenticated ingestion is disabled by default. Persist readings separately from NASA observations. An integration sketch copy at `esp32/SoilSense_v1/SoilSense_v1.ino` preserves the supplied local dashboard and adds AP+STA plus periodic HTTP uploads. Do not claim ESP32 compatibility or offline upload has been hardware-tested.

## Controlled growing and habitat monitoring

The Space Crop Research page must preserve the existing Research and Farmer Dashboard features and provide:
- Experiment creation with crop, variety, location, dates, research objective and named treatment groups.
- Timestamped group measurements with explicit source IDs and units.
- Per-plant height, leaf-count and visible-stress observations.
- Harvest plant count, fresh mass, and optional measured dry mass.
- Habitat readings for temperature, humidity, light, medium moisture, water/reservoir, and optional CO2, nutrient pH and EC.
- Device metadata for sensor types, calibration notes and units.
- Crop profiles that require titled URL references whenever nutrition values are supplied.
- Descriptive growth rate, yield per plant and fresh/dry biomass per recorded litre of water. Do not calculate results from missing values; do not include unassigned water in group comparisons.
- Group-comparison plant-height chart and downloadable study report with methods, sources and limitations.

Manual habitat entry is acceptable for the first software prototype. The current ESP32 integration measures soil moisture only. Additional SHT31, BH1750, flow, CO2, pH or EC sensors require separate wiring, firmware libraries, calibration and hardware validation. Lux is not PPFD. Do not seed example crop values or completed experimental results as if observed.

Use the protocol in `docs/experiment-protocol.md`; report Earth-based experiments as terrestrial controlled growing, not microgravity or spacecraft life-support tests.
